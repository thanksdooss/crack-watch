# 00. 접근법 선택 — 균열 검출·폭 추정

작성 2026-09-21. 1단계(기술 조사와 선택)의 결과물.

## 0. 이 문서가 정하는 것

- 사진에서 균열을 찾는 방법으로 무엇을 쓸 것인가 (고전 영상처리 / 학습 모델 / 조합)
- 학습·평가에 쓸 공개 데이터셋은 무엇이고, 각각 어떤 라이선스인가
- 그 선택의 근거와 위험, 그리고 숫자로 검증할 방법

정하지 않는 것: 신고 검증 로직, 서버 스키마, 화면 설계 (2단계 이후).

## 1. 제약 조건 먼저

선택은 아래 제약에서 나온다. 성능 논문 순위가 아니라 이 제약이 기준이다.

| 제약 | 내용 | 영향 |
| --- | --- | --- |
| 기기 내 추론 기본 | 서버에 이미지를 올리지 않는 모드가 기본값. 브라우저(PWA)에서 추론 | 모델 크기·추론 시간이 정확도만큼 중요 |

| 설명 가능성 | 신고가 반려될 때 왜인지 말할 수 있어야 함 | 전부 블랙박스면 운영에서 못 쓴다 |

## 2. 접근법 세 가지 비교

### (a) 고전 영상처리
가우시안 블러 → CLAHE → 적응 이진화(또는 Frangi/Hessian 선형 구조 강조) → 형태학 연산 → 연결요소 필터(길이·세장비·면적) → 스켈레톤 + 거리변환으로 폭 산출.

- **장점**: 학습 데이터가 필요 없다. 모델 다운로드 0MB, OpenCV.js(WASM)로 한 장 수십~수백 ms. 실패했을 때 어느 단계에서 틀렸는지 눈으로 볼 수 있다. 폭 계산이 파이프라인에서 자연스럽게 나온다.
- **단점**: 콘크리트 표면은 균열이 아닌 선형 구조로 가득하다 — 거푸집 자국, 줄눈, 전선 그림자, 빗물 자국, 타일 경계. 임계값은 조명마다 흔들리고, 재현율을 올리려 임계를 낮추면 오탐이 폭증한다. 우리 제품에서 오탐은 곧 신고 채널의 신뢰 하락이다.

### (b) 세그멘테이션 모델 파인튜닝
U-Net 계열(경량 인코더) 또는 SegFormer-B0을 공개 균열 데이터로 학습 → ONNX 변환·양자화 → 브라우저 추론.

- **장점**: 텍스처·그림자·얼룩에 훨씬 견고하다. 공개 데이터가 픽셀 마스크까지 있어 학습이 가능하다. 임계값 튜닝 대신 데이터로 성능을 올릴 수 있다.
- **단점**: (1) 모바일 브라우저 예산 — WebGPU는 아직 실험적이고 iOS 지원이 고르지 않아 WASM 폴백이 필수인데, WASM은 네이티브 대비 크게 느리다. (2) **마스크 두께가 폭이 아니다.** 세그멘테이션 출력은 이진화 임계에 따라 굵어지고 얇아지며, 1~2px 균열에서는 경계가 뭉개져 폭을 과대추정한다. 폭(mm)을 마스크 두께로 재면 오차가 임계값에 종속된다. (3) 틀렸을 때 설명할 수단이 없다.

### (c) 조합
모델이 **어디가 균열인가**를 정하고(검출·영역 분리), 고전 CV가 **얼마나 벌어졌나**를 잰다(중심선을 따라 원본 그레이스케일 단면의 반치폭으로 서브픽셀 폭 추정). 색 보정(기준 패치)과 기준 물체 스케일 환산도 고전 CV 쪽.

- **장점**: (b)의 약점인 폭 편향을 (a)로 막고, (a)의 약점인 오탐을 (b)로 막는다. 모델이 없거나 다운로드 실패해도 (a)만으로 동작하는 저사양 경로가 남는다. 기준선 숫자가 그대로 보존되어 "모델이 얼마나 나은가"를 항상 비교할 수 있다.
- **단점**: 구현·평가 대상이 두 배. 단계가 늘어 디버깅 지점이 많다.

### 라이선스 취급 원칙

1. **저장소에 데이터셋 이미지를 넣지 않는다.** 스크립트가 원 배포처에서 받아오게 하고, 받은 경로는 `.gitignore` 처리한다.
2. **CC0/CC BY만 학습에 쓴다.** 비상업 한정 데이터(DeepCrack·CFD 등)는 논문 수치 비교 참고로만 언급하고 학습에 넣지 않는다.
3. **집합 데이터셋의 상위 라이선스 리스크를 인지한다.** CrackSeg9k는 CC0으로 게시되어 있으나 구성 요소 중 일부(DeepCrack, CFD 계열)는 원 배포처에서 비상업 조건을 달고 있다. 집합체의 CC0 선언이 원 저작자의 조건을 자동으로 덮는다고 보지 않는다. 그래서 우리는 **(가) 데이터셋 이미지를 재배포하지 않고, (나) 학습 가중치만 배포하며, (다) 상업적 사용을 주장하지 않고, (라) 출처를 전부 표기**한다. 이 판단과 한계를 README에도 그대로 쓴다.
4. 샘플·데모 이미지는 **본인이 촬영한 무특징 벽면**만 쓴다. 주소·간판·사람이 보이지 않게 찍고 EXIF를 제거한다(GPS 포함).

### 데이터의 한계 — 도메인 갭

공개 데이터는 대부분 포장도로를 정면·근접에서 찍었다. 우리 시나리오는 **시민이 길에서 스마트폰으로, 비스듬히, 제각각 조명에서** 찍는다. 그래서 공개 데이터의 IoU가 좋아도 현장 성능은 보장되지 않는다. **평가의 최종 기준은 자체 촬영 평가셋**이고, 공개 데이터 점수는 학습이 진행되고 있다는 보조 지표로만 읽는다.

## 4. 선택

### **(c) 조합을 고른다. 단, 순서를 지켜서.**

```
0) 색 보정 (기준 패치)      ← 먼저. 색을 못 믿으면 아래 전부가 흔들린다
1) 고전 CV 기준선            ← 모델 없이 여기까지가 baseline
2) 평가셋 + 지표 고정        ← 숫자가 없으면 3)의 가치를 증명 못 한다
3) 모델 학습 → 경량화 → 교체 ← 기준선 대비 개선폭을 수치로
4) 폭 추정: 모델 영역 + 원본 단면
```

**근거 네 가지**

1. **폭 추정이 고전 CV를 필수로 만든다.** (b)만 고르면 마스크 두께로 폭을 재야 하는데, 그 값은 이진화 임계에 종속된다. 어차피 중심선·거리변환·단면 프로파일 코드를 쓸 거라면, 그 코드를 기준선으로 먼저 완성하는 게 순서상 맞다.
2. **비교 대상이 없는 성능 수치는 의미가 없다.** "IoU 0.7"은 그 자체로 아무 말도 하지 않는다. 같은 평가셋에서 고전 CV가 0.35라면 그때 0.7이 의미를 갖는다. 기준선을 먼저 만드는 건 모델을 위한 준비가 아니라 **주장을 검증 가능하게 만드는 절차**다.
3. **저사양 폴백이 필요하다.** 대상 사용자는 기기를 고를 수 없다. 모델 로딩 실패·메모리 부족·구형 브라우저에서 앱이 아무것도 못 하면 캠페인은 거기서 끝난다. (a)가 항상 동작하는 바닥이 된다.
4. **라이선스가 깨끗한 학습셋이 실제로 있다.** CrackSeg9k(CC0) + SDNET2018/Özgenel(CC BY)만으로 학습이 성립한다. 비상업 데이터에 손대지 않아도 된다.

### 모델 후보 (3단계에서 확정)

- 1순위: **U-Net + 경량 인코더**(MobileNetV3-Small 또는 ResNet-18). 구조가 단순해 ONNX 변환에서 미지원 연산자 문제가 적다.
- 2순위: SegFormer-B0. 성능은 유리하나 ONNX Runtime Web에서 연산자 지원·양자화 호환을 먼저 확인해야 한다.
- 런타임: **ONNX Runtime Web**, WebGPU 우선 + **WASM(SIMD) 폴백 필수**. WebGPU 백엔드는 아직 실험적이고 양자화 연산자 지원이 고르지 않아, 양자화 모델은 WASM 경로를 기준으로 잡는다.
- 목표치(**측정값이 아니라 목표**, 3~4단계에서 실측):
  - 모델 파일 10MB 이하(int8)
  - 중급 안드로이드, WASM 경로, 512×512 한 타일 기준 2초 이내
  - 자체 평가셋 IoU가 고전 CV 기준선보다 유의하게 높을 것

### 평가 지표 (2단계에서 `docs/evaluation.md`로 고정)

- 검출: IoU, 정밀도/재현율/F1 — 균열은 픽셀이 극히 희소하므로 **정확도(accuracy)는 쓰지 않는다**(전부 배경이라 예측해도 99%가 나온다).
- 폭: 자로 실측한 기준값 대비 **평균절대오차(mm)** 와 오차 범위. 균열 폭 구간별(0.3mm 이하 / 0.3~1mm / 1mm 초과)로 나눠 본다.
- 색: 기준 패치 보정 전후의 색차(ΔE), 조명 조건(주광·형광등·석양)별.
- 속도: 기기별 1장 처리 시간(로딩 제외/포함).
