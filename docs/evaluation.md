# 평가 — 기준선 대비 얼마나 나은가

`python -m ml.eval.detection <엔진>` → `python -m ml.eval.detection render`로 다시 만든다.
이 파일의 숫자는 `docs/results/*.json`에서 자동으로 옮긴 것이다.

## 지표 읽는 법

- **정밀도**: 균열이라고 표시한 것 중 진짜 균열의 비율. 낮으면 헛신고가 많다.
- **재현율**: 진짜 균열 중 찾아낸 비율. 낮으면 놓친다.
- **F1**: 둘의 조화평균. 한쪽만 좋아서는 올라가지 않는다.
- **IoU**: 표시한 영역과 정답 영역이 겹친 정도. 1px만 어긋나도 깎이는 엄격한 지표.
- **허용 F1(2px)**: 정답에서 2px 안이면 맞춘 것으로 친다. 1~2px짜리 균열은 라벨 경계 자체가
  ±1px 흔들려서, 엄격 IoU만 보면 방법 간 차이가 라벨 잡음에 묻힌다.
- **헛경보율**: 균열 없는 벽 사진에서 '균열 있음'이라고 한 비율. 제품에서 가장 비싼 실수.
- 정확도(accuracy)는 쓰지 않는다 — 균열은 이미지의 1~3%라 전부 배경이라고 답해도 97%가 나온다.

## 1. 실제 사진 — CrackSeg9k test

건물 벽면(Rissbilder·Volker·Masonry)이 우리 제품이 실제로 찍힐 표면이다.

## 2. 합성 test — 정답 폭을 아는 세트

> 합성 데이터다. 빗물 자국·거푸집 이음선·기공 같은 '균열처럼 생긴 가짜'를 일부러 넣었다.
> 실제 성능의 증거가 아니라, 무엇에 속는지를 조절하며 보는 실험대다.

| 엔진 | IoU | 정밀도 | 재현율 | 허용 F1 | 헛경보 (균열 없는 벽) |
| --- | ---: | ---: | ---: | ---: | ---: |
| 고전 CV (기준선) | 0.798 | 91.0% | 86.7% | **0.983** | 0.0% (0/15) |
| U-Net+MobileNetV3 (32비트, 배포) | 0.194 | 55.3% | 22.9% | **0.394** | 0.0% (0/15) |

### 요약

실제 건물 벽면에서 모델의 허용 F1은 기준선의 **2.6배**(0.294 → 0.759), IoU는 **3.6배**(0.115 → 0.413). 균열 없는 벽 헛경보는 51% → 2.5%.

반대로 합성 세트에서는 기준선이 0.983, 모델이 0.394다. 합성 균열은 '배경 위의 깨끗한 검은 선'이라 고전 CV에 유리하고, 실제 사진으로 학습한 모델에게는 낯설다. 합성 세트는 폭 정답이 필요한 실험(아래 3절)에만 쓰고 검출 성능 판단에는 쓰지 않는다.

기준선의 헛경보율은 분할마다 크게 흔들렸다(val 60장 10% → test 163장 51%). 민무늬 벽의 원본 사진 수가 적어 분할마다 벽 질감이 다르기 때문이다. 기준선은 벽 질감에 민감하다는 것 자체가 결과다.

## 3. 폭 추정 오차 (합성 test — 정답 폭을 앎)

기준 카드에서 오는 축척 오차는 빼고, **폭 측정 자체**의 오차만 본다. '검출 마스크'는 기준선이 낸 마스크로 잰 것 — 실제로 쓰일 조건이다.

**검출 마스크로 잼** — 평균절대오차 mm (편향)

| 폭 구간 | n | 마스크 두께 | 반치폭 | 넓이 기반 | **채택(혼합)** |
| --- | ---: | ---: | ---: | ---: | ---: |
| 0.3mm 이하 (머리카락 굵기) | 2218 | 0.152 (+0.148) | 0.154 (+0.153) | 0.106 (+0.102) | 0.105 (+0.101) |
| 0.3~1mm | 6350 | 0.256 (+0.238) | 0.109 (+0.106) | 0.122 (+0.107) | 0.104 (+0.098) |
| 1mm 초과 | 5010 | 0.226 (-0.141) | 0.110 (+0.008) | 0.207 (+0.098) | 0.110 (+0.008) |

**정답 마스크로 잼** — 평균절대오차 mm (편향)

| 폭 구간 | n | 마스크 두께 | 반치폭 | 넓이 기반 | **채택(혼합)** |
| --- | ---: | ---: | ---: | ---: | ---: |
| 0.3mm 이하 (머리카락 굵기) | 3445 | 0.101 (+0.098) | 0.174 (+0.174) | 0.107 (+0.099) | 0.109 (+0.101) |
| 0.3~1mm | 6441 | 0.090 (+0.076) | 0.098 (+0.094) | 0.115 (+0.099) | 0.093 (+0.085) |
| 1mm 초과 | 5539 | 0.076 (+0.036) | 0.117 (-0.030) | 0.216 (+0.093) | 0.117 (-0.030) |

마스크 두께로 재면 검출기의 이진화 임계에 폭이 끌려간다(0.3~1mm 구간에서 가장 크게 벌어짐). 채택한 방법은 중심선을 따라 **원본 밝기 단면**에서 잰다: 폭 4px 미만은 넓이 기반(흐림에 강함), 이상은 반치폭(균열 폭의 10%만큼 단면을 평활해 바닥의 기공에 끌려가지 않게). 남은 +0.1mm 안팎의 과대추정은 합성 데이터의 흐림 모델에서 나온 것이라 실제 사진에 그대로 빼지 않는다 — 과대추정은 '전문가 점검 권장' 쪽이라 안전한 방향이다.

## 4. 경량화 — 8비트 양자화를 채택하지 않은 이유

| 설정 | 크기 | 32비트 대비 마스크 IoU | 허용 F1 (val 60장) |
| --- | ---: | ---: | ---: |
| fp32 | 6.17 MB | 1.000 | 0.793 |
| 정적 MinMax, 전체 | 1.90 MB | 0.103 | 0.247 |
| 정적 Percentile, 전체 | 1.90 MB | 0.256 | 0.454 |
| 정적 MinMax, 출력층 제외 | 1.92 MB | 0.103 | 0.247 |
| 정적 MinMax, 출력층+마지막 디코더 제외 | 2.08 MB | 0.103 | 0.247 |
| 정적 MinMax, 인코더만 | 3.71 MB | 0.103 | 0.248 |
| 정적 Percentile, Conv만 | 1.89 MB | 0.327 | 0.531 |
| 동적(가중치만) | 1.74 MB | 0.075 | 0.196 |

어떤 설정도 32비트를 따라가지 못했다. 디코더·출력층을 빼도 그대로라 문제는 인코더(MobileNetV3)이고, 가중치만 양자화해도 무너진다 — 깊이별 합성곱은 채널마다 값 범위가 크게 달라 8비트 하나에 담기 어렵다. 양자화를 고려한 재학습(QAT)이 다음 단계이고, 지금은 32비트(6.2MB, 목표 10MB 이하)를 배포한다.

## 5. 처리 시간

브라우저: chromium 153.0.8010.12 (Apple Silicon 데스크톱), 합성 샘플 3장 × 3회 중 첫 실행을 뺀 중앙값. 사진 긴 변 1,200px, 모델 입력 긴 변 1,024px, 웹 워커 1스레드(WASM).

| 엔진 | 전체 | 카드·색 보정 | 균열 검출 | 폭 측정 |
| --- | ---: | ---: | ---: | ---: |
| 고전 CV | 0.9 s | 52 ms | 591 ms | 292 ms |
| 모델(32비트) | 1.1 s | 51 ms | 732 ms | 267 ms |

| 기기 | 상태 |
| --- | --- |
| 데스크톱 브라우저 (위 표) | 실측 |
| 중급 안드로이드 / 아이폰 | **미측정** — 실기기가 필요하다 |

처음엔 같은 방법으로 4.3초가 나왔는데, 그때는 같은 기계에서 학습·격자 탐색이 돌고 있었다. 한가할 때 다시 재고 배포본(공개 주소)에서도 교차 확인해 위 값으로 바로잡았다 — 배포본 실측은 고전 CV 0.96초, 모델 1.15초였다.

휴대폰 근사로 크롬의 CPU 4배 감속을 써 봤지만 감속이 웹 워커에 걸리지 않아(감속했는데 오히려 빨라짐) 버렸다. 목표였던 '중급 안드로이드에서 512px 타일 2초 이내'는 아직 확인하지 못했다. 모델 파일 크기 목표(10MB 이하)는 6.2MB로 충족.

## 평가 규칙

- 파라미터·모델·폭 측정 방법 선택은 합성 dev와 CrackSeg9k val에서만 한다. test는 보고용으로만 쓴다.
  (폭 측정 방법을 한때 합성 test로 비교했다가 되돌려 dev에서 다시 골랐다 — docs/decisions.md)
- CrackSeg9k 분할은 **원본 사진 단위**로 나눴다. 한 장을 잘라 만든 조각들이 train과 test에
  갈라져 들어가면 test가 train을 베낀 셈이 되어 점수가 부풀려진다.
- 비상업·등록 조건이 명시된 하위 세트(DeepCrack·CFD·GAPs)는 학습과 평가 모두에서 뺐다.
- 처리 시간은 파이썬·데스크톱 CPU 1스레드 기준이다. 브라우저·휴대폰 시간은 따로 잰다.
