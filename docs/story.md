# 이야기 — 왜 시작했나, 용어, 어떤 불편을 어떻게 풀었나

포트폴리오 케이스(`crack-watch.js`)에 들어간 내용의 원본. 불편 세 가지는 [`decisions.md`](decisions.md)에 개발하며 그때그때 적은 기록에서 뽑았다.

## 왜 시작했나

오래된 건물 벽에 금이 가도, 그게 얼마나 벌어졌는지 재서 알릴 방법이 시민에게는 없다. 2024년 아이디어 대회에서 우리 팀은 "늘어나면 붉게 변하는 필름을 붙이고, 붉어지면 시민이 사진으로 신고하게 하자"는 기획서를 냈지만, 필름은 다른 기관의 기술이라 기획서로 끝났다. 2년 뒤 다시 보니 캠페인이 무너지는 곳은 필름이 아니라 사진이었다. 해질 무렵에는 파란 것도 붉게 찍히고, 장난·중복 신고가 몇 번만 쌓여도 담당자는 신고 채널 자체를 믿지 않게 되기 때문이다.

## 처음 보는 용어라면

| 용어 | 한 문장 |
| --- | --- |
| 균열 폭 | 벽에 간 금이 벌어진 너비. 국내 건축물 안전점검 지침은 응력에 의한 균열이 0.3mm를 넘으면 보수를 권한다 — 이 앱은 이 값을 판정이 아니라 "전문가 점검 권장"으로 넘어가는 안내선으로만 쓴다. |
| 기준 카드 | 색과 크기를 이미 아는 인쇄물을 균열 옆에 붙여 같이 찍으면, 사진의 색이 얼마나 틀어졌는지와 1픽셀이 몇 mm인지를 거꾸로 계산할 수 있다. |
| 세그멘테이션 모델 | 사진의 픽셀 하나하나에 "균열이다 / 아니다"를 칠하는 AI. 여기서는 휴대폰 브라우저 안에서 돌도록 작게 만들었다. |
| 지각 해시 (사진 지문) | 사진의 대략적인 모습을 0과 1 64개로 줄인 값. 같은 장면이면 비슷하게 나와 중복 신고를 찾을 수 있고, 원본 사진은 되살릴 수 없다. |
| F1 · 헛경보율 | F1은 "찾아낸 것 중 맞은 비율"과 "있는 것 중 찾아낸 비율"을 함께 본 점수(1이 만점), 헛경보율은 균열 없는 벽을 균열이라고 한 비율 — 신고 앱에서 가장 비싼 실수. |

## 어떤 불편을, 어떻게 풀었나

### 1. 사진 속 색을 믿을 수 없다

- **불편**: 원래 기획의 질문은 "표지가 붉게 변했는가"인데, 같은 벽도 해질 무렵엔 주황, 형광등 아래선 초록빛으로 찍힌다. 조명 탓에 파란 표지가 붉게 보이면 멀쩡한 건물이 신고된다. 보정이 잘 됐다는 걸 증명하는 것도 문제였다 — 기준 색 전부로 보정을 맞추면 그 색들이 잘 맞는 건 당연하다.
- **한 일**: 인쇄용 기준 카드(색 칸 6 + 모서리 사각형 4 + 60mm 자). 보정 계수는 흰·회색·검정 칸에서만 구하고 빨강·파랑은 채점용으로만. 같은 카드의 모서리 사각형으로 축척과 원근까지.
- **확인**: 합성 조명 최악 조건 색차 ΔE 14.0 → 2.6, "붉은가" 오판 5/24 → 0/24, 카드 축척 오차 0.1% 이내(합성). 실제 스마트폰 실측은 미측정.

### 2. 폭을 재는 방법이 검출기에 끌려간다 — 정답도 없다

- **불편**: AI가 칠한 영역의 두께로 폭을 재면 AI가 얼마나 진하게 칠하느냐에 따라 폭이 달라진다. 공개 데이터셋에는 실제 폭(mm) 정답이 없어 비교할 수도 없었다.
- **한 일**: 폭을 정해 놓고 그리는 합성 벽면 생성기로 정답 확보. 폭은 중심선을 따라 원본 밝기 단면에서. 넓은 균열 바닥의 기공이 "가장 어두운 점"이 되는 문제는 균열 폭 비례 평활로, 가는 균열은 넓이 기반으로.
- **확인**: 0.3~1mm 균열 평균 오차 0.256 → 0.104 mm. 한때 test 분할을 보고 방법을 고르던 실수를 되돌려 dev에서 다시 골랐다.

### 3. 중복·장난 신고를 거르는 기준이 가정이었다

- **불편**: "같은 장면이면 지문 차이 14 이하"로 가정했는데, 실제 벽 사진 180장으로 재 보니 재촬영 차이의 중앙값이 16. 첫 시뮬레이션에서 나쁜 신고를 43%밖에 못 걸렀다.
- **한 일**: 측정한 분포로 용도별 기준(묶기 18 · 중복 8 · 다른 위치 12). 정답 라벨을 아는 신고 흐름 시뮬레이션으로 규칙의 구멍(지도 칸 경계 버그, 재저장 사진, 도배 전 틈 → 소급 보류)을 찾았다. 걸린 신고는 지우지 않고 사유와 함께 보류.
- **확인**: 나쁜 신고 자동 보류 43% → 82.7%, 중복 병합 100%, 정상 신고 억울한 보류 0.2%(합성 흐름). '엉뚱한 건물'은 3분의 1만 잡고, 그럴듯한 가짜는 사람 몫.

## 면접 대비 질문

### 1. 고전 영상처리 기준선을 먼저 만든 이유는?

세 가지다. (1) **비교 대상 없는 숫자는 아무 말도 안 한다.** "IoU 0.41"은 같은 시험에서 기준선이 0.12라는 걸 알 때 의미가 생긴다. (2) **폭 측정이 어차피 고전 영상처리를 필요로 했다.** 중심선·단면·세선화 코드를 쓸 거라면 그걸로 기준선을 먼저 완성하는 게 순서였다. (3) **저사양 폴백.** 모델 로딩이 실패하면 앱이 아무것도 못 하는 대신 고전 CV로 돈다(실제로 브라우저에서 모델이 안 불러와졌을 때 이 경로가 작동했다).

덧붙여 기준선을 **공정하게** 만드는 데 신경 썼다. 합성 데이터에서만 조정하면 실제 사진에서 억울하게 낮아져 모델 개선폭이 부풀려진다. 그래서 기준선도 실제 사진 val로 3라운드 격자 탐색을 했고, 최적값이 탐색 범위 가장자리에 걸리면 범위를 넓혔다. 그 결과가 실제 벽면 F1 0.294 → 0.759다. 반대로 합성 세트에선 기준선이 이긴다는 것(0.98 vs 0.39)도 함께 보고했다.

### 2. 픽셀에서 실제 mm로 환산할 때의 오차 요인은?

1. **해상도 한계** — 픽셀보다 가는 건 못 잰다. 오차 범위에 항상 ±0.5px을 넣고, 1.5px 미만이면 "이 해상도로는 구분하기 어렵다"고 알린다.
2. **흐림** — 가는 균열은 흐림 폭만큼 넓게 보인다. 넓이 기반 측정으로 줄였지만 합성 실험에서 여전히 약 +0.1mm 과대추정이 남았다.
3. **축척(px/mm)** — 기준 카드 검출 정확도. 모서리 꼭짓점 16개를 예측과 비교한 오차를 축척 불확실성에 반영한다.
4. **원근(비스듬히 찍음)** — 방향마다 배율이 달라진다. 비스듬한 정도를 재서 불확실성에 더하고, 15%를 넘으면 판정을 보류하고 다시 찍어 달라고 한다.
5. **카드와 균열이 같은 평면인가** — 사진 한 장으로는 확인할 수 없다. 사용 안내("같은 벽면, 바로 옆")로 대신한다.
6. **인쇄 배율** — 카드가 축소 인쇄되면 모든 환산이 틀어진다. 카드에 60mm 자를 넣어 사용자가 확인하게 했다.

그래서 폭은 단일 숫자가 아니라 항상 범위로 보여 주고, 범위의 **상단**이 0.3mm에 닿으면 대표값이 그 아래여도 "전문가 점검 권장"을 띄운다.

### 3. 사용자가 잘못 판단할 위험을 어떻게 줄였나?

- 화면 어디에도 "안전합니다·위험합니다"를 쓰지 않는다. 안내는 "관찰 필요 / 전문가 점검 권장 / 판정 보류" 세 가지뿐이고, 고지문이 결과 옆에 항상 붙는다(E2E로 단언).
- 폭은 항상 오차 범위와 함께, 판단은 보수적으로(범위 상단 기준).
- 기준 카드가 없으면 mm를 **지어내지 않는다**(판정 보류). 모델이 실패하면 조용히 넘어가지 않고 어떤 엔진으로 돌았는지와 사유를 표시한다.
- "넓어지는 중"은 두 시점의 **오차 범위가 겹치지 않을 때만** 말한다. 대표값만 비교하면 측정 흔들림을 변화로 오인한다.
- 고지문에 "급하게 위험해 보이면 앱이 아니라 119·관할 구청에"를 넣었다.

### 4. 이 앱을 실제 지자체가 쓰려면 무엇이 더 필요한가?

- **실측 검증**: 실제 스마트폰으로 찍은 사진에서의 검출 성능, 캘리퍼스로 잰 폭과의 비교, 중급 휴대폰 처리 시간 — 지금은 전부 미측정이다.
- **위치를 건물 대장에 연결**: GPS 오차가 25m로 나빠지면 중복 병합이 67%로 떨어진다. 주소·동 번호로 묶는 게 확실하다.
- **운영 체계**: 기관 계정 인증(SSO), 조치 이력 보존 정책, 보류 대기열을 누가 언제 보는지의 업무 흐름, 신고자에게 결과를 알려 주는 경로.
- **법·책임**: 앱 안내가 행정 판단으로 오해되지 않도록 하는 고지와 약관, 위치정보 수집 동의 절차 검토.
- **규모**: 신고가 수만 건이 되면 사진 지문 검색 색인(BK-트리 등), 모델 경량화(양자화를 고려한 재학습).
